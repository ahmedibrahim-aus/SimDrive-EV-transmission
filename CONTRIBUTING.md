# Contributing

Issues and pull requests are welcome.

## Release validation

Run `buildtool release` in a clean MATLAB session (the integration tests use
the base workspace). Dashboard end-to-end tests run the real simulation, edit a
control after completion, and verify the exported summary and student ZIP.
The module is tested on MATLAB R2025b and R2026b on Windows, and on R2025b on
Linux in CI; R2025a has not been tested. The dashboard test
(`tInstructorWorkflow`) opens the app window and needs a display. On a headless
machine either run it under a virtual display (Xvfb), as the full-release CI
job does, or run `buildtool check testFast`, which leaves it out.

For hosted CI on a private copy of the repository, configure the GitHub Actions secret
`MLM_LICENSE_TOKEN` with a valid MathWorks batch licensing token. The workflow
maps it to the environment variable required by MathWorks. Never commit the
token. See the [official run-build licensing instructions](https://github.com/matlab-actions/run-build#use-matlab-batch-licensing-token).

The tests that contain reference answers are inside the encrypted
`instructor_answer_key.7z`. To run them in CI, set the secret
`ANSWER_KEY_PASSWORD`; without it CI runs every other test.
Before tagging a release, run the **MATLAB validation** workflow on GitHub; the
manual and weekly runs execute the complete `release` target.

Please keep changes scoped and reproducible:

1. Run `check_dependencies` in MATLAB before reporting runtime problems.
2. Do not commit generated artifacts such as exported `.mat` files, PNG plots, or autogenerated Simulink build outputs.
3. Preserve MATLAB R2025a+ release compatibility unless there is a documented reason to raise the minimum version.
4. Keep instructor-facing outputs traceable to the equations documented in `MathematicalModels.md`.
5. Update `README.md`, `Contents.m`, and `CITATION.cff` when a release changes repository metadata.

For release changes, review `docs/release-checklist.md` before tagging a version.

## Maintainer tools

`tools/buildStudentPackage.m` builds the student hand-out and needs nothing
beyond the MATLAB products the module already requires.

`tools/build_project_brief.py` regenerates
`student_package/EV_Gearbox_Project_Brief.docx` and needs
[python-docx](https://python-docx.readthedocs.io/):

```bash
python -m pip install python-docx
python tools/build_project_brief.py
```

This is a maintainer dependency, not a course requirement. Students and
instructors running the module never need Python. Edit the brief by editing the
script and regenerating, not by editing the `.docx`, or the next rebuild will
discard the change. The script sets the document properties explicitly, so the
regenerated file carries the author's name and the build date rather than the
python-docx template defaults.
